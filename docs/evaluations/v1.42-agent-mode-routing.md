# V1.42 Agent Mode Routing Checkpoint

Date: 2026-07-18
Status: completed and deployed
Linear issue: SCA-6
Target version: V1.42.0

## Objective

Validate that one active agent tag and multi-tag capability eligibility reduce
irrelevant automatic context without restricting on-demand API Mind use,
inventing sensor behavior, or treating a stored posture as autonomous
execution.

## Starting Runtime

- `idle`, `interactive`, and `scouting` are registered agent tags.
- Human-facing native and GPT turns deterministically use `interactive`.
- `idle` and `scouting` are persistable resume postures; `interactive` is
  system-owned.
- `scouting` has no sensor or autonomous runtime.
- Automatic runtime blocks are routed by tag; shell commands remain available
  independently.
- The canonical V2 model document receives only the allowlisted organ blocks
  that survive rich-context routing.

## Initial Evidence

Focused baseline tests passed 23/23 across `test_agent_modes.py` and
`test_mind_shell.py`. Existing direct evidence proves one natural mode change,
one persistent setting, a current `interactive` override, and an explicit
no-autonomous-runtime receipt. It does not prove model behavior in a real
non-conversational `idle` or `scouting` cycle because no such cycle exists.

The current routing receipt has two systemic defects:

1. it reports only block types, without block id, matched capability, required
   tags, delivery result, or reason;
2. in `off` and `shadow`, it reports mode-ineligible blocks outside
   `included_block_types` even though the router returns and delivers them.

Measured baseline for an `idle` decision:

| Routing mode | Returned block ids | Reported included types | Reported ineligible types |
| --- | --- | --- | --- |
| `off` | session, message, affect, unknown | session, unknown | message, affect |
| `shadow` | session, message, affect, unknown | session, unknown | message, affect |
| `active` | session, unknown | session, unknown | message, affect |

The active row is internally coherent; the off/shadow rows conflate policy
eligibility with actual delivery. This is a trace-contract bug, not stochastic
LLM behavior.

The persistence invariant is also enforced only by the shell handler. The
lower-level `set_preferred_agent_mode` primitive accepts `interactive`, so a
future internal caller could create a state that the public command forbids.

## Approved Implementation Contract

- Emit one ordered decision per input block with id, type, capability,
  capability status, required tags, eligibility, delivery disposition,
  delivered flag, and reason.
- Preserve aggregate compatibility fields while making `included` and
  `excluded` describe actual delivery.
- Distinguish `off`, `shadow`, and `active`: off observes no enforcement,
  shadow records `would_exclude` but delivers, active excludes ineligible
  registered blocks.
- Keep unregistered block types fail-open and visibly classified so registry
  drift cannot silently delete new context.
- Enforce resumable-mode ownership in the storage primitive as well as the
  shell boundary.
- Keep every shell family callable in every mode.
- Add no sensor, webhook, autonomous cycle, background mode, or new tag.

3. Canonical V2 projection checks proving only delivered allowlisted organ

## Human Decisions Deferred

No decision is needed for this slice. A future real idle/scouting execution
cycle, sensor routing, or new agent mode requires a separate design discussion
and cannot be inferred from this validation.

## Final Implementation

- Routing now derives filtering and aggregates from one ordered per-block
  receipt containing block id, type, capability, status, required tags,
  eligibility, delivery disposition, delivered flag, and reason.
- `off` reports every delivered block, `shadow` reports both delivery and
  `would_exclude`, and `active` reports actual exclusions.
- Unregistered block types remain fail-open and visible instead of disappearing
  because the capability registry has not caught up.
- The persistence primitive rejects the system-owned `interactive` tag, not
  only the shell handler.
- Native and GPT prompts now distinguish selection semantics: `idle` means no
  direction to resume, while `scouting` is a valid exploratory orientation
  even before sensors or autonomous execution exist.
- The deterministic preliminary provider now distinguishes metacognitive output
  from answer-obligation judging. This repaired the gate fixture without
  weakening the runtime's fail-closed validator.

## Direct Scarlet Evidence

The bounded direct check used one fresh disposable copy per attempt and the
existing natural `BEH-0011`/`BEH-0012` two-session chain.

The first attempt preserved `idle`. Scarlet interpreted the explicit absence
of sensors and autonomous execution as a reason not to select `scouting`. This
matched the earlier V1.34 ambiguity and was classified as a systemic selection-
policy gap, not a transient model miss or router failure.

After the prompt and registry clarified the positive meaning of scouting, the
second attempt passed both technical contracts:

- turn `turn_13aa5e5b38ae45caba6f47ec675e96bd` called
  `mode set scouting`, persisted `resume_tag=scouting`, kept the current turn
  `interactive`, and explicitly denied sensor/autonomous execution;
- separate-session turn `turn_567d4326ce60440f870968d455f0a085`
  recovered scouting without another mode mutation and kept the active human
  turn interactive;
- both runtime traces contained ordered per-block receipts for
  `session.continuity`, `scarlet.agent_mode`, `turn.perception`, and
  `scarlet.dynamic_state`, all with explicit capabilities and delivery reasons.

Scarlet also wrote the user's post-conversation posture as a semantic
preference. That write was sourceable and consistent with memory policy, but it
was not required to make mode persistence work and is not counted as router
evidence.

## Acceptance Boundary

SCA-6 is accepted for implemented human-turn routing, persistence, traceability,
native/GPT parity, and on-demand shell independence. It does not validate an
idle/scouting agent cycle, sensor context, environmental perception, webhook
handling, or autonomous work. Those require a real runtime and a new checkpoint.
