# V1.58 Physical Device Exploration

Date: 2026-07-26
Status: background and foreground physical runs complete
Device scope: one physical Samsung SM-S918B, Android 14 / API 34
App scope: Scarlet V1.58.0 baseline and V1.58.1 network-fix APK

## Evidence Contract

The observations in this report were emitted by the installed APK through
Capacitor plugins. No device payload was synthesized from ADB. The device had
no usable network transport while locked, so an ephemeral CDP request
interceptor forwarded the APK's unchanged exploration API requests through the
development computer to the protected VPS. CDP also opened the existing
`?screen=device` review route because the secure lock prevented normal touch
navigation.

This transport workaround did not create observations, alter payloads, or
admit device data into Scarlet's cognitive runtime.

## Qualitative Findings

### Automatic snapshots

Device, app, battery, permission, and notification capability payloads were
stable and internally coherent across runs. Raw payloads preserve plugin
specific detail, while normalized payloads expose the fields needed for
cross-device comparison.

The network plugin consistently returned `connected=false` and `none`. The
outbox retained 18 observations across multiple app restarts and emptied after
transport became available. Resubmitting one real `client_event_id` returned
`accepted=0`, `deduplicated=1`, and did not increase the ledger count.

### Position

Both precise and approximate permissions were `granted`. The explicit
high-accuracy request returned `explicit_position_error` with
`Could not obtain location in time`. This is valid evidence for the tested
background/locked condition, not proof that foreground positioning is broken.

### Notifications

The app created the `scarlet-device-lab` channel with vibration enabled and
received a successful scheduling receipt. A later snapshot still found one
pending notification and no delivered notification. No received or interaction
event was emitted. Foreground/unlocked behavior and Android exact-alarm policy
remain open experimental variables.

### Haptics

The success effect completed through the native plugin and produced a persisted
`haptics.success_feedback` receipt. This is the first verified outbound device
actuation in the exploration ledger.

### Motion and lifecycle

No sampled motion or active/resume lifecycle event was observed because the
secure lock kept the activity in background. These probes are untested in this
run, not failed.

## Isolation Check

After all 51 observations, production still contained 241 sessions, 930
messages, 313 memories, 238 memory facts, and 6,675 cognitive events. The new
ledger contained 51 rows. Focused integration tests independently prove that
observation writes create no session, memory, or trace.

Every summary response reported:

```json
{
  "model_context_delivery": false,
  "cognitive_persistence": false
}
```

## Implementation Findings

Direct use exposed two confirmed defects:

1. `GET /observations?probe=...` filtered returned rows but reported a total
   across all probes.
2. Initial UI refresh could race the debounced snapshot upload, temporarily
   showing `Storico run = 0` after six observations had been emitted.

V1.58 now applies the probe filter to `total` and awaits the initial snapshot
flush before the screen requests run history.

## Unlocked Foreground Run

The unlocked run completed the deferred foreground checks without synthetic
device payloads.

### Location

The same explicit high-accuracy request that timed out while locked completed
in foreground. Both location permissions remained granted, the reported
accuracy was about 17 meters, and speed was effectively stationary. Exact
coordinates remain only in the protected raw ledger and are intentionally
excluded from this report.

This distinguishes an Android execution-condition difference from a broken
location probe.

### Notifications

One local notification completed the full lifecycle:

```text
schedule_requested -> received -> action_performed(tap)
```

All three records carried the same notification id. This proves scheduling,
delivery, plugin callback reception, and user interaction as separate
observable boundaries.

### Lifecycle

Sending the app to Home and reopening it produced:

```text
pause(false) -> app_state_change(false)
-> app_state_change(true) -> resume(true)
```

The observations retained their device timestamps and reached the same
exploration run after resume.

### Motion

Foreground motion sampling ran at the configured three-second cadence over
native samples reporting a 16 ms source interval. In a stationary 37-sample
window:

- acceleration excluding gravity remained zero;
- gravity magnitude ranged from `9.8833` to `9.9910`;
- beta ranged from `-5.0` to `-4.9` degrees; and
- gamma ranged from `-5.8` to `-5.7` degrees.

Alpha crossed the `0/360` boundary, so a future consumer must use circular
angle treatment rather than arithmetic averaging. Deliberately moved-device
comparison remains unmeasured because ADB cannot physically manipulate the
handset; this is a residual experiment, not a probe failure.

### Network And V1.58.1 Fix

A real Wi-Fi disable/enable cycle exposed the expected transition through no
transport and cellular before Wi-Fi recovered. The baseline controller also
recorded many identical connected-Wi-Fi callbacks while no semantic network
state changed. Run `device_run_c7ff23367abd4db9ba8bfea32c409c52` accumulated
67 network records, revealing that uploads could provoke another native
network callback and sustain technical self-observation.

V1.58.1 suppresses only consecutive callbacks with the same connectivity and
transport pair. In physical run
`device_run_01187b58aef444539ff454faed17d5e0`:

- network history remained at one snapshot while motion grew from 8 to 20
  samples over 35 seconds; and
- a second Wi-Fi disable/enable cycle still produced
  `wifi -> none -> cellular -> wifi`, with no loss of distinct states.

The device was left with Wi-Fi restored.

## Residual Exploration

The next useful physical experiments are deliberately moving the handset to
compare motion windows, measuring longer background/outbox intervals, and
deciding which normalized signals warrant a separately approved perception
proposal. None of those signals is currently admitted to Scarlet.
