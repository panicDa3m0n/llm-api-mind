# V1.38 Historical Provenance Audit

Date: 2026-07-18
Issue: Linear SCA-20
Status: accepted, deployed, and verified in production

## Objective

Classify historical memory provenance without turning similarity into truth,
separate read-only evidence from mutation, and make every accepted maintenance
operation reproducible, backup-bound, and inspectable.

## Safety Boundary

- Production was inspected read-only before implementation.
- Local verification used temporary databases or disposable copies.
- `backend/data/app.db` was not used as a writable target and remains outside
  this change.
- No record is hard-deleted.
- Semantic duplicate/conflict adjudication, user ownership, and probabilistic
  source attribution are out of scope.

## Production Starting Condition

The read-only audit against
`/opt/scarlet-mobile-test/backend/data/app.db` inspected 307 memories:

| Provenance class | Count | Initial interpretation |
|---|---:|---|
| Complete source hook | 61 | Session, turn, and stored message present under the legacy audit; role was not validated. |
| Missing session or turn | 242 | Required structured inspection; not safe to repair from the class alone. |
| Invalid stored source message | 4 | Stored message disagreed with the declared source turn. |

The database hash remained unchanged across each individual audit call. The
live production database could change between calls because real sessions were
active; therefore candidate-set digests, rather than a frozen whole-file hash,
are the apply-time drift guard.

## Classification Evidence

All 242 session-only records carried the complete explicit fixture contract:

1. metadata keys `codex_test_dataset_version`, `codex_test_key`, and
   `codex_test_lane`;
2. tags `codex-test` and `codex-dirty-memory-v1`; and
3. a resolvable source session whose title begins `Codex Test Seed - `.

They belong to exactly three seed sessions: user preferences, metacognitive
lessons, and project/API Mind. They were created in one bounded seed interval;
241 were active and one was already deprecated. This is deterministic test-data
contamination, not an LLM interpretation and not evidence that the semantic
contents are duplicates.

The strict V2 contract also requires the source message to be a user message.
It therefore reports seven invalid links rather than the legacy four: three
point to an assistant message inside the declared turn, three point to an
assistant message in a different turn, and one points to a user message in a
different near-duplicate turn. More than one semantic origin is plausible.
They therefore remain retained, review-only, and excluded from automatic V2
memory hints. The system must not rewrite them from similarity.

No exact normalized-content duplicate group was present in this production
inventory.

## Implemented Contract

`memory-provenance-audit-v2` emits two orthogonal classifications:

- provenance validity: missing, invalid, session-only, exact-repairable,
  ambiguous, invalid-message, or complete-valid;
- record disposition: sourceable, exact-source repair, explicit fixture,
  exact-duplicate review candidate, or retained non-sourceable review.

The GET audit is always read-only. Exact source repair and explicit fixture
deprecation use separate POST routes. Real apply requires all of:

- prior dry-run;
- exact approval token;
- reviewed SHA-256 digest of the complete candidate id set;
- verified backup reference; and
- unchanged candidate set at apply time.

Explicit fixture deprecation updates canonical memory/fact lifecycle and
derived retrieval artifacts, adds append-only audit activity, excludes that
activity from recent-memory selection, and does not touch the historical source
session timestamp.

Code transfer excluded `backend/data/`, `.env`, virtual environments, caches,
and evaluator artifacts. The candidate image passed a read-only
production-role preflight against the persistent mount before service restart.
`/health` then reported version `1.38.0`, production/direct database ownership,
and healthy runtime state.

The live read-only audit and dry-run reproduced the reviewed candidate digest.
The guarded apply, bound to the backup above, deprecated 241 active fixture
memories and created 241 non-recent maintenance activities. Independent raw
SQLite verification established:

- all 242 fixture memories are now deprecated, including the one already
  inactive before apply;
- 202 associated facts and 1,412 derived surfaces are deprecated across the
  complete 242-record fixture set;
- no active canonical memory overlaps the reviewed fixture ids;
- the three seed-session timestamps equal their pre-apply values;
- the seven unresolved source links remain active and review-only; and
- live and backup SQLite integrity are both `ok`.

The remote retrieval configuration had two stale values after deployment: the
old `0.01` rerank floor and an OpenRouter backend paired with the local-hash
default embedding model name. Runtime configuration was aligned to the V1.37
contract (`0.004` absolute floor, `0.01` relative floor, Nvidia embedding and
rerank models) and the service was restarted. A post-fix GPT bridge control for
`zenzero infuso sera tisana` completed both embedding and rerank, returned zero
memories, and finalized successfully (`turn_7e3c5ff5bb06416188f6dbc111bcfee5`).

A natural native Scarlet control also found no active ginger-infusion memory
and did not receive the deprecated fixture in automatic context, shell results,
or provider input. This accepts SCA-20. Two independent observations remain
outside its scope: one native turn ended with only a public work note (tracked
under SCA-28), and one unrelated active Context Router memory scored `0.004102`
for a negative tea-preference query (recorded under SCA-3 for follow-up
calibration).

## Residual Risk

- The seven inconsistent/non-user links require future semantic/human adjudication or
  new exact evidence; they are not repaired in V1.38.
- Lifecycle operations commit through existing repository boundaries. The
  backup and digest guards provide recovery and drift protection; broader
  atomic maintenance-job orchestration belongs to the organ/maintenance rework.
- Deprecated source records remain inspectable history by design. Retrieval
  must continue filtering inactive canonical and derived artifacts.
