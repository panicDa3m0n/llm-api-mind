# V1.41 Answer Obligations Checkpoint

Date: 2026-07-18
Status: implemented, verified, and deployed
Linear issue: SCA-28
Target version: V1.41.0

## Objective

Prevent the runtime from accepting a public progress note as Scarlet's final
answer and make objective runtime evidence operational in the answer when the
turn requires it. The implementation must preserve natural-language freedom:
the backend may enforce a traced obligation, but it must not decide ambiguous
meaning through substring rules, hand-authored scores, or automatic rewriting.

## Starting Evidence

Two independent gaps define the slice:

- BUG-0085: native session `ses_02f95bf1a9874b0cb3fa5cd613377897`,
  turn `turn_fc2045c3b17542b6812c1df8f1994279`, ended with provider
  `end_turn` and non-empty public text that was only a work note. The backend
  persisted it and completed the turn because the text was non-empty.
- BUG-0011: the runtime exposed a memory conflict and unavailable capability
  state, but the answer could omit the conflict or offer an unavailable
  operation. Retrieval itself had succeeded; the missing layer was answer
  control.

The V1.40 longitudinal organ evaluation reproduced the first boundary during a
volition chain: the model publicly announced a check, emitted no tool call, and
the turn completed. The following session correctly found that no intention had
been written. This separates answer-boundary failure from organ persistence.

## Current Runtime Boundary

Native MiniMax:

- `AnthropicCompatibleProvider.stream_chat_with_tools` treats every terminal
  non-empty text block without a tool call as a final answer;
- `chat.py` rejects only empty terminal text before persisting the assistant
  message and completing the turn;
- text in a provider message without a tool call is currently classified as
  `assistant_answer`, even when its semantic role is only progress narration.

External GPT:

- `/gpt/bootstrap` opens the turn and returns runtime context;
- `/gpt/action` executes the same Mind shell used by native Scarlet;
- `/gpt/finalize` is already an explicit transport-level final boundary, but
  currently accepts every non-empty draft without answer-obligation validation.

## Approved Contract

### Severity

- `hard`: a failed obligation blocks persistence and turn completion;
- `warning`: the answer may continue, but the finding is traced;
- `advisory`: model-facing orientation with no blocking effect.

### Obligation Sources

Obligations are derived from evidence already present in the current turn:

- an explicit final-answer boundary for native provider completion;
- active conflicts delivered in the memory context;
- source-sensitive requirements selected by the existing metacognitive trigger
  layer;
- current capability state when the user is asking about capabilities;
- completed or failed Mind shell actions observed during the turn.

Regex or deterministic cues may route a candidate to the semantic validator;
they must never decide whether free text actually satisfies an obligation.

### Validation And Recovery

- structural completion is checked deterministically;
- semantic obligations are judged through one compact structured LLM review
  only when at least one such obligation exists;
- the validator returns per-obligation `pass`, `fail`, or `unknown`, with a
  concise reason and evidence references;
- a hard failure permits one bounded correction attempt;
- native Scarlet receives an internal continuation request in the same turn;
- GPT finalize returns a recoverable rejection and keeps the turn active, so
  the GPT can correct the draft and call finalize again;
- a second hard failure fails explicitly; the backend does not invent or
  rewrite Scarlet's answer;
- a rejected draft is traced but is never stored as the canonical assistant
  message or provider history.

### Observability

The implementation records:

- `answer.obligations` for the compiled manifest;
- `answer.validation` for each draft review;
- `answer.recovery.requested` when a hard failure causes correction;
- the manifest and final validation trace ids in the normal response trace.

The GPT bootstrap mirrors the same manifest in compact form through
`action_policy`, `required_actions`, and `recommended_actions`. The model may
change, but the runtime contract does not.

## Out Of Scope

- deciding whether two semantically similar memories are genuine conflicts;
- adding new lifecycle or cognitive organs;
- coupling answer validation to the metacognition organ;
- deterministic natural-language rewriting;
- autonomous cycles or user-task execution;
- treating ordinary stylistic weakness as a hard runtime defect.

Focused deterministic tests and a small direct native/GPT probe are sufficient
for this issue. The full multi-hour behavioral suite remains owner-triggered.

## Residual Risks To Measure

- the provider may occasionally omit the structural final marker twice;
- semantic validation adds latency only to obligated turns and can itself be
  inconclusive;
- external GPT correction depends on the GPT respecting a recoverable finalize
  error;
- stream clients can see work notes before the corrected final answer, which is
  intentional public progress, while only the accepted answer becomes the
  canonical assistant message.

## Implemented Surface

- `backend/app/runtime/answer_obligations.py` owns manifest compilation,
  severity, tool-evidence augmentation, model-facing rendering, semantic
  judgment, and GPT action policy.
- Native sync and stream use the same enforcement loop. The first rejected
  provider message stays in provider continuity for one correction but is not
  stored as an assistant message.
- Active streaming suppresses draft text and terminal answer events until the
  accepted final is available. Public notes produced in actual tool-use steps
  and tool lifecycle events remain visible.
- GPT bootstrap returns the initial manifest, actions return the augmented
  manifest, and finalize enforces one recoverable rejection.
- `context.accounting.preflight` measures the native obligation appendix as its
  own channel.
- Prompts and the checked-in GPT Actions schema describe the same runtime
  distinction between executable actions and answer obligations.
