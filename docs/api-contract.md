# API Contract

This file documents stable API contracts once they are implemented.

## Response Philosophy

Mind API responses should be useful to both code and the LLM agent.

Successful responses should follow this shape where practical:

```json
{
  "ok": true,
  "result": {},
  "cognitive_hint": "Short explanation of how this result may matter.",
  "suggested_next_actions": [],
  "confidence": 0.8,
  "trace_id": "trace_..."
}
```

Error responses should be structured and recoverable when possible:

```json
{
  "ok": false,
  "error": {
    "code": "namespace.error_name",
    "message": "Human-readable error.",
    "recoverable": true
  },
  "suggested_next_actions": [],
  "trace_id": "trace_..."
}
```

## Field Ownership Policy

Status: accepted principle, pending full schema annotation

API Mind is Scarlet's internal cognition, but deterministic operational fields
belong to the backend. Route bodies should ask Scarlet only for information that
requires model judgment.

Backend-owned fields:

- ids for sessions, turns, messages, traces, memories, facts, tool calls, and
  provider messages when they are generated by the current operation;
- current time, `created_at`, `updated_at`, `recorded_at`, lifecycle event
  timestamps, latency, usage counters, and summary freshness metadata;
- source provenance for live operations, including current
  `source_session_id`, `source_turn_id`, and `source_message_id` when available;
- transcript message counts, last included message id, summary coverage, and
  trace ids.

Scarlet-owned fields:

- semantic memory content, type, reason, expected future use, confidence,
  salience, scope, tags, and non-provenance metadata;
- memory/session/fact search queries, filters, selected existing target ids,
  and lifecycle reasons;
- metacognitive objective, mode, focus question, internal prompt, evidence
  summary, uncertainties, draft answer, and previous-step summaries.

Implementation note:

Current handlers already stamp most provenance and timestamps in the backend.
The contract still needs per-route `agent_supplied_fields` and
`backend_owned_fields` metadata in `/mind/schema`, plus sanitization for
backend-owned fields if the model sends them inside free-form metadata.

## Implemented Internal Runtime Context

Status: implemented

Purpose:

Build backend-owned operational context before each LLM call. This is not a public user-facing endpoint. It is an internal chat-runtime phase that makes memory evidence perceptual and traceable instead of depending only on optional model tool calls.

Target turn flow:

```txt
POST /api/chat/sessions/{session_id}/turn
-> build TurnFrame
-> automatic memory retrieval
-> ranking, exclusions, conflicts
-> persist memory.context trace
-> compose block-based runtime.context trace
-> inject <runtime_context> into the model request
-> run MiniMax tool loop with model-controlled cognitive operations
-> persist answer and traces
```

```json

    "turn_id": "turn_...",
    "block_index": [],
    "blocks": [],

    "temporal_context": {},
    "capabilities": {}
  }

```

Required behavior:

- Every chat turn creates `memory.context`, even when no memory is selected.
- Every chat turn creates `runtime.context`, with stratified
  `session_context`, `message_context`, and `scarlet_state` blocks.
- Every chat turn exposes a single configured `temporal_context.now` to the
  model. The default timezone is `Europe/Rome`; dashboard settings may change
  it. Scarlet should use this before making claims such as "now", "today",
  "how long ago", or duration estimates.
- The current platform language is provided by
  `message_context.current_message.language`. It is a dashboard/runtime
  setting, not automatic language detection.
- The active user profile is provided by
  `message_context.user_profile.identity`. It is operational state for
  recognition, personalization, user-scope memory boundaries, and future
  multi-user privacy separation.
- The configured locale is provided by `message_context.world.location`. It is
  country/timezone-level runtime evidence for local calendar and time
  reasoning, not GPS or exact physical presence.
- `session_context` is continuity evidence only. Session summaries are
  navigation aids and do not replace source transcript reads for exact claims.
- `message_context` is current-turn perception and includes automatic memory
  retrieval, user-profile hints from active user-scope memories, temporal
  world data, recent runtime events, and API Mind schema/capability metadata.
- `scarlet_state` is backend-seeded operational state for focus and open loops;
  it is not a claim of human emotion and is expected to become API-managed in a
  future slice.
- The backend may inspect more candidates internally than it injects into the model request.
- Selected candidates are the only memory records that should be treated as evidence by the model.
- Near misses and exclusions remain trace evidence for debugging and evaluation.
- Missing memory claims should be considered verified only when `memory.context.searched=true` or an explicit memory search result supports them.
- Capability state in runtime context is the source of truth for implemented and unavailable memory actions.

Current retrieval plan:

1. Implemented: SQLite FTS5/BM25 sparse retrieval over backend-built search
   documents for memory context and manual memory/session search.
2. Implemented: relevance guard that separates `selected`, `near_miss`, and `excluded`.
3. Implemented: simple conflict grouping over selected active memories that appear to describe the same subject.
4. Implemented: temporal filters for manual memory/session search, resolved by
   the backend from runtime time rather than by model-side date arithmetic.

Deferred retrieval plan:

- Dense embeddings for paraphrases.
- Hybrid sparse+dense rank fusion.
- Cross-encoder reranking.
- Post-response validator for unverifiable memory claims.

## MVP Storage Schema

Status: implemented

Purpose:

Provide the persistence foundation for chat tracing, tool calls, semantic
memory records, canonical memory facts, and episodic session summaries.

Tables:

- `sessions`: conversation/project session container, including
  `provider_history_json`, the Anthropic-compatible provider-native message
  history used for future model calls.
- `turns`: one user-to-assistant processing cycle, including model, status, latency, and error metadata.
- `messages`: user, assistant, system, or tool messages linked to sessions and optionally turns.
- `traces`: structured JSON trace events linked to sessions and optionally turns.
- `events`: ordered runtime event records linked to sessions, turns, traces,
  tool calls, and messages. Events are the runtime control-plane stream used by
  the cockpit, next-turn context, and background triggers.
- `maintenance_jobs`: backend-owned asynchronous maintenance jobs, currently
  used for per-session idle maintenance after completed turns.
- `tool_calls`: structured model-facing tool calls, arguments, results, status, and latency.
- `memories`: Scarlet's persistent Memory v0 records with source provenance, confidence, salience, metadata, usage counts, and timestamps.
- `memory_facts`: canonical facts linked to memories, with entity, predicate,
  value JSON, temporal fields, source provenance, lifecycle status, and
  fact-level supersession links.
- `memory_proposals`: pending or resolved memory maintenance candidates
  generated by review processes. Proposals are not active memories; they store
  evidence, suggested action, similar-memory ids, related fact ids, and future
  embedding/graph-ready decision metadata.
- `session_summaries`: episodic recall index records linked one-to-one to chat
  sessions, with a descriptive summary, topics, decisions, open questions,
  source message counts, and memory ids written from that session.
- `search_documents_fts`: SQLite FTS5 sparse search index for backend-built
  memory and session documents. It is a derived index, not canonical memory
  state.

Trace And Event Behavior:

Trace rows store JSON payloads. Chat, tool, memory, lifecycle, and fact
operations write dedicated trace kinds when they run with session context.
Event rows store ordered operational facts such as turn lifecycle, memory
context, model request/response, tool-call lifecycle, public work notes, and
final answers. Events are compacted into `<runtime_context>.recent_runtime_events`
on following turns. Maintenance job rows store scheduled/running/completed
status, due time, trigger turn/event, supersession, input payload, result
payload, and error payload.

## Implemented Runtime Events

Status: implemented

Purpose:

Provide an ordered event spine for runtime behavior, not only debug
traceability. Traces remain the deep forensic record; events are the compact,
chronological operational layer used by the UI and by Scarlet's next-turn
context.

Event shape:

```json
{
  "id": "evt_...",
  "session_id": "ses_...",
  "turn_id": "turn_...",
  "seq": 7,
  "type": "mind.tool_call.completed",
  "source": "mind_api",
  "actor": "backend",
  "visibility": "debug",
  "status": "completed",
  "parent_event_id": "evt_...",
  "trace_id": "trace_...",
  "tool_call_id": "tool_...",
  "message_id": null,
  "payload": {},
  "created_at": "2026-05-23T12:00:00+00:00"
}
```

Current emitted event types include:

- `turn.started`, `turn.completed`, `turn.failed`
- `message.user.persisted`, `message.assistant.persisted`
- `memory.context.built`
- `llm.request.created`, `llm.request.started`, `llm.response.completed`
- `mind.tool_call.started`, `mind.tool_call.completed`,
  `mind.tool_call.failed`
- streamed provider milestones such as `mind.tool_call.requested`,
  `mind.tool_call.result_returned`, and `llm.request.stopped`
- `assistant.note.emitted`, `assistant.answer.completed`
- `llm.thinking.captured` with metadata only, not raw private thinking text.
- `maintenance.job.scheduled`, `maintenance.job.started`,
  `maintenance.job.completed`, `maintenance.job.skipped`,
  `maintenance.job.failed`
- `maintenance.memory_review.completed`

Runtime use:

- The streaming frontend renders live `runtime_event` rows during the turn.
- The frontend renders persisted activity blocks from events first, falling
  back to traces only for older turns without events.
- `build_memory_context` includes compact recent events from previous turns in
  `<runtime_context>.recent_runtime_events`.
- Session idle maintenance is scheduled after `turn.completed`. A newer turn in
  the same session supersedes or skips the older pending job; other sessions
  are independent.
- The idle job currently runs `sessions.summarize`, missed semantic memory
  review, and pending memory proposal creation. It does not write active
  semantic memories automatically.

### GET /api/debug/events

Status: implemented

Purpose:


### POST /api/chat/sessions/{session_id}/turn

Status: implemented

Purpose:

Persist a user message, call MiniMax with the session history, persist the
assistant response, and store request/response traces.

Provider execution policy: Anthropic-compatible model calls use provider
streaming internally. This endpoint still returns one final response object; the
stream is collected inside the backend.

The model-facing history is built from `sessions.provider_history_json` when
available. This field stores Anthropic-compatible `user`/`assistant` messages
with native content blocks such as `text`, `thinking`, `tool_use`, and
`tool_result`. The normal `messages` table remains the human-readable chat
history used by the UI and episodic recall. For older sessions without provider
history, the backend reconstructs a text-only provider history from persisted
`user`/`assistant` messages once, then persists native provider history after
the next completed turn.

Request:

```json
{
  "message": "Reply with exactly: pong",
  "system": null,
  "max_tokens": null
}
```

`max_tokens` is optional. When omitted, the backend uses the selected provider
default token budget.

For MiniMax M2.7, the backend accepts request overrides up to `131072`, matching
the documented maximum completion budget.

`system` is optional. When omitted or blank, the backend loads the configured agent system prompt. The default prompt is `backend/app/prompts/scarlet_system.md`. It can be replaced with `AGENT_SYSTEM_PROMPT` or `AGENT_SYSTEM_PROMPT_PATH`.

Response:

```json
{
  "session": {
    "id": "ses_...",
    "title": "Baseline trace",
    "created_at": "2026-05-08T15:00:00Z",
    "updated_at": "2026-05-08T15:00:01Z",
    "metadata": {}
  },
  "turn_id": "turn_...",
  "status": "completed",
  "user_message": {
    "id": "msg_...",
    "role": "user",
    "content": "Reply with exactly: pong"
  },
  "assistant_message": {
    "id": "msg_...",
    "role": "assistant",
    "content": "pong"
  },
  "trace_ids": ["trace_...", "trace_...", "trace_..."],
  "model": "MiniMax-M2.7",
  "latency_ms": 1104,
  "usage": {
    "input_tokens": 26,
    "output_tokens": 16
  }
}
```

Errors:

- `404 session.not_found`: the session does not exist.
- `503 agent.system_prompt_error`: the configured agent system prompt could not be loaded.
- `503 llm.not_configured`: the selected provider key is missing
  (`MINIMAX_API_KEY` or `QWEN_API_KEY`).
- `502 llm.provider_error`: the selected upstream provider request failed.

Trace Behavior:

Creates at least:

- `memory.context`
- `llm.request`
- `llm.response`

When the model uses `mind_api`, the turn also creates one `mind.tool_call` trace per tool invocation.

When the model uses Memory v0 through `mind_api`, the turn also creates:

- `mind.memory.write`
- `mind.memory.search`
- `mind.memory.read`
- `mind.memory.facts`
- `mind.memory.facts.backfill`
- `mind.memory.deprecate`
- `mind.memory.supersede`
- `memory.conflicts`

`llm.request` stores the effective system prompt plus:

- `system_present`
- `system_source`: `bundled`, `environment`, `configured_path`, or `request`
- `system_path` when loaded from a file
- `base_system`: the stable configured system prompt before runtime context injection
- `runtime_context`: the backend-generated runtime context block passed to the model
- `memory_context_trace_id`: the associated `memory.context` trace row
- `tool_loop_policy`: currently `model_controlled_unbounded`
- `provider_history_source`: either `session.provider_history_json` or
  `messages.text_reconstructed`
- `provider_message_stats`: message count, content-block count, JSON character
  count, and an approximate token estimate for the model-facing history
- `provider_messages`: the exact provider-facing messages sent to the selected
  Anthropic-compatible provider for this turn
- `tools`: currently the single `mind_api` tool schema

If the provider fails, creates:

- `llm.error`

`llm.response` stores final text, usage, raw final content, normalized tool call metadata, and raw provider messages from the tool loop when tools were used.

non-streaming endpoint, but stream model and agent-loop events to the debug
cockpit before the final response is complete.

Provider execution policy: this endpoint forwards the same provider-streaming
events that the non-streaming endpoint collects internally.

Request:

```json
{
  "message": "Use mind_api before answering.",
  "system": null,
  "max_tokens": 131072
}
```

Response:

The response is newline-delimited JSON with media type `application/x-ndjson`. Each line has:

```json
{
  "type": "text_delta",
  "data": {
    "seq": 15,
    "turn_id": "turn_...",
    "model_step": 2
  }
}
```

Every streamed event includes `data.seq`, a monotonically increasing turn-local sequence number, and `data.turn_id`, so clients can render the exact operation order inside the correct assistant turn. Provider events tied to a specific model request include `data.model_step`; `model_request` events also include `data.step`.

Current event types:

- `turn_started`: persisted user message and turn identifiers are ready.
- `runtime_event`: one persisted `CognitiveEvent` row emitted live as soon as
  the backend writes it. The event is available at `data.event`.
- `memory_context`: automatic memory context was built and traced before the model request.
- `model_request`: a provider request step started.
- `thinking_start`: provider-exposed thinking block started.
- `thinking_delta`: provider-exposed thinking text delta for debug inspection.
- `tool_use_start`: provider tool-use block started.
- `tool_input_delta`: partial JSON input streamed by the provider for the tool call.
- `tool_call`: normalized tool call before backend dispatch.
- `tool_result`: normalized result returned by the backend dispatcher.
- `text_start`: final text block started.
- `text_delta`: assistant response text delta.
- `model_stop`: provider stop reason for the current model step.
- `turn_complete`: final `ChatTurnResponse` after messages, traces, and turn status are persisted.
- `error`: recoverable stream error object.

Errors:

- `404 session.not_found`: the session does not exist.
- `503 agent.system_prompt_error`: the configured agent system prompt could not be loaded before streaming starts.
- Provider/runtime errors after streaming starts are emitted as `error` events and persisted as failed turn traces.

Trace Behavior:

Creates the same persistent trace records and runtime events as
`POST /api/chat/sessions/{session_id}/turn`. `llm.request` and `llm.response`
payloads include `"stream": true`; tool calls still create `mind.tool_call`
traces, `tool_calls` rows, and event lifecycle rows.

Live Event Behavior:

The streaming endpoint emits `runtime_event` lines for persisted event rows
during the turn. Events created before the provider stream starts
(`turn.started`, `message.user.persisted`, `memory.context.built`, and
`llm.request.created`) are replayed immediately after `turn_started`. Provider
milestones, Mind API tool-call lifecycle events, assistant public notes, final
answer, `turn.completed`, and `maintenance.job.scheduled` are emitted as they
are persisted.

## Implemented Mind API

Mind API is Scarlet's internal cognitive interface. It is exposed to the model
as the single `mind_api` tool, but it is not a normal user-operated API during
conversation. The user states goals in natural language; Scarlet decides when
to inspect schema, search memory, inspect facts, or perform traceable state
changes before answering.

Chat turns use a model-controlled, unbounded tool-loop policy:

```txt
tool_loop_policy = model_controlled_unbounded
```

The loop continues until Scarlet returns a final answer instead of another
`mind_api` call. Provider errors, network failures, or process-level failures
can still interrupt a turn, but the backend does not impose a fixed
`max_tool_calls` cap.

### GET /mind/sessions through mind_api

Status: implemented

Purpose:

List recent chat sessions as Scarlet's episodic recall index. This is not
semantic memory search; it is a way for Scarlet to discover which prior
conversations may contain relevant history before opening the exact transcript.

Model-facing call shape:

```json
{
  "method": "GET",
  "path": "/mind/sessions",
  "intent": "Find recent sessions that may contain memory-design context.",
  "body": {
    "limit": 10,
    "offset": 0,
    "query": "episodic recall",
    "time": {
      "preset": "yesterday",
      "basis": "conversation"
    }
  }
}
```

Compatibility behavior:

- query-string paths such as `/mind/sessions?limit=10` are normalized into the
  body before dispatch;
- `top_k`, `count`, `page_size`, `last`, and `recent` map to `limit`;
- `q` maps to `query`.
- `when`, `period`, and `date_range` map to `time`.

Temporal behavior:

- `time.preset` accepts `today`, `yesterday`, `last_7_days`, and
  `this_session`.
- `time.from` and `time.to` accept ISO dates or datetimes; date-only values are
  resolved by the backend as local-day boundaries.
- `time.basis=conversation` filters by user/assistant message timestamps.
- `time.basis=created`, `updated`, or `summary` filters by session creation,
  update, or summary freshness timestamps.
- `this_session` returns only the calling session.
- Query search uses the backend FTS5/BM25 sparse index over session title,
  summary fields, and conversation text, with a deterministic text-match
  fallback.

Response result:

```json
{
  "operation": "sessions.list",
  "query": "episodic recall",
  "time": {
    "preset": "yesterday",
    "basis": "conversation",
    "resolved": {
      "from": "2026-05-23T00:00:00+00:00",
      "to": "2026-05-24T00:00:00+00:00"
    }
  },
  "retrieval_stages": ["fts5_sparse_v1", "fallback_summary_text_match_v1"],
  "count": 1,
  "has_more": false,
  "sessions": [
    {
      "id": "ses_...",
      "title": "Episodic recall design",
      "summary": {
        "summary": "Compact description of the conversation substance.",
        "topics": ["episodic recall"],
        "decisions": ["Semantic memory remains separate from session recall."],
        "memory_ids": ["mem_..."],
        "status": "active"
      },
      "memory_ids": ["mem_..."]
    }
  ]
}
```

If no stored summary exists, the response includes a deterministic
`status=fallback` description so Scarlet can still navigate the session list.
That fallback is a weak navigation aid, not durable evidence.

Errors:

- `sessions.context_required`: session listing requires a calling session so the
  model-facing operation can be traced through `mind.tool_call`.
- `sessions.invalid_body`: body shape is invalid after normalization.

Trace Behavior:

The read-only list operation is represented by the surrounding `mind.tool_call`
trace. It does not mutate cognitive state.

Every successful memory search creates `mind.memory.search` and increments usage metadata on returned memories. The model-facing call still creates `mind.tool_call`.

Search scoring includes fact text when facts exist, so aliases such as
`Zero Light protocol` can match a canonical `protocollo-zero-luce` fact even
when the narrative memory used another language. This is still sparse lexical
retrieval, not dense semantic embedding.
